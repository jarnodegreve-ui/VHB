# PlanX — VHB-personeelsportaal

Portaal voor het busbedrijf (GitHub-repo `jarnodegreve-ui/VHB`). Vite + React + TS + Tailwind (`src/`), serverless API (`api/`), Supabase. Prod = Vercel-project `vhb` → vhb-five.vercel.app (Pro). **`vhb-planner` is een ánder Vercel-project** (rostering) — nooit daarheen deployen.

## Git & sessies
- **Nooit `git add -A`** — parallelle sessies delen deze working tree (rostering/, losse WIP). Stage expliciete paden; voor gedeelde bestanden (api/index.ts, vercel.json): aparte git-worktree vanaf origin/main.
- Features landen via feature-branch + PR, niet rechtstreeks op main.
- `rostering/` = geneste eigen repo (CP-SAT-solver, eigen memory) — niet aanraken tenzij gevraagd.

## API & deploy
- **Elk bestand in `api/` wordt een aparte Vercel-functie.** Gedeelde modules → `api/_lib/` (underscore bouwt niet als functie). vercel.json rewrites sturen alles naar api/index.ts.
- Deploy verifiëren via Vercel-MCP (`list_deployments`, `get_deployment_build_logs`) — niet met curl-salvo's (bot-challenge) of de GitHub-deployments-API. Functionele marker: nieuw endpoint 401 = live, 404 = oud. Bundel-hash lokaal vs. live vergelijken werkt NIET.
- Crons in vercel.json, CRON_SECRET-beveiligd (Pro: frequenter dan dagelijks mag).
- **Gedeelde API-contracten (zod)** staan in `shared/schemas/` (repo-root, naast `api/` en `src/` — géén cross-import api↔src). Eén schema per record (user, diversion, update) valideert het formulier én de request-body; de NL-foutteksten per veld staan dáár. `api/` importeert `../shared/schemas/x.js`, `src/` `../../shared/schemas/x`; Vercel traceert imports buiten `api/` gewoon mee en `shared/` wordt geen functie (staat niet onder `api/`); tsconfig en vitest nemen `shared/` mee. Server bij fouten: 400 `{ error: 'Ongeldige invoer', details, veldfouten: { veld: tekst } }` (`api/_lib/valideer.ts`); client: `src/lib/valideer.ts` (`valideer` + `veldfoutenUitAntwoord`) → Field error-prop, en `perRecord(…, opVeldfouten)` brengt server-veldfouten naar het formulier.

## Database
- Supabase met **quoted camelCase-identifiers** (anders dan snake_case elders). Migraties handmatig in SQL Editor, idempotent; hergebruik `public.set_updated_at()` en `current_app_user_role()` uit setup_security.sql. Kolomnamen moeten matchen met api/storage.ts + api/types.ts. Elke .sql eerst langs de `supabase-sql-reviewer` (hook doet dit automatisch).
- **Staging** = apart Supabase-project `vhb-portaal-staging` + Vercel-Preview-env; opzet, SQL-volgorde en env-vars in `supabase/staging/README.md`; testdata `supabase/staging/seed.sql` (idempotent, prefix `stg-`, e-mail `@staging.vhb.test`, vangrail tegen productie) + `node scripts/staging-accounts.mjs` (Auth-accounts + `users.authid`). Nieuwe migratie → ook op staging draaien en onderaan de README-lijst bijschrijven. **Beleidsdrift**: elke migratie die RLS, policies, grants of definer-functies raakt → na het draaien `node --env-file=.env.local scripts/beleid-drift.mjs --update` en `supabase/beleid-snapshot.json` mee committen (nachtelijke check in `.github/workflows/beleid-drift.yml`, README › Beleidssnapshot). `VITE_OMGEVING=staging` toont het stille label (`OmgevingLabel`) in topbar en login; leeg = productie.

## Prestaties
- **Lighthouse CI** (job `lighthouse`, `.lighthouserc.json`): mobiel, 5 runs/mediaan, login + `/mijn-dag` via `scripts/lighthouse-server.mjs` (dist + brotli + e2e-fixtures als API-mock). Scores blokkeren (perf ≥ 0,9 login / ≥ 0,75 Mijn dag; a11y ≥ 0,95, best-practices ≥ 0,9), metrics waarschuwen (LCP ≤ 2,5 s, CLS ≤ 0,1, TBT ≤ 300 ms). **Waarom 0,75 op Mijn dag** (10-09): de mediaan van de runner schommelt daar tussen 0,73 en 0,83 terwijl dezelfde code lokaal stabiel 0,82-0,83 haalt — de oude 0,80 lag midden in die ruis en viel willekeurig om, wat de check waardeloos maakte. Gecontroleerd met een lokale 3-runs-meting van 0544632 (06-09) tegen main: 0,83 vs 0,82, dus géén regressie; de eerder genoteerde 0,87 was een gunstige CI-run. TBT en CLS zijn 0, het knelpunt is FCP/LCP en dat is inherent aan client-rendering (de gemeten `<h1>` bestaat pas na ~225 kB JS). Echt hoger vraagt voorrenderen van de schil, geen drempelwerk. Zakt de mediaan onder 0,75, dán is er wél iets stuk. Lokaal: bouwen met `VITE_SUPABASE_URL=http://localhost:4191` + dummy anon key, dan `npx --yes @lhci/cli@0.14.0 autorun`; rapporten in `.lighthouseci/rapporten/`. Bundelbudget blijft `scripts/check-bundle-size.mjs`.
- **Laden**: nav-items prefetchen hun view bij hover/aanraken (`prefetchView`, NavItem `onPrefetch` + BottomNav); na login warmt App.tsx bij idle dashboard/Mijn dag/rooster + de rol-schermen op; `vite.config.ts` bakt een `<link rel="preconnect">` naar de Supabase-origin in (alleen https, dus niet in e2e/Lighthouse).
